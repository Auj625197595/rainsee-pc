# 扩展后台 Service Worker 启动延迟 30 秒问题排查记录

## 现象

项目启动后，MV3 扩展（Tampermonkey）的后台 Service Worker 大约要 **30 秒**才开始运行，
期间没有任何用户操作。表现为 `[ext-sw] alarm: init done` 这类日志在进程启动约 +30s 时才出现。

## 排查过程（逐步用计时日志定位）

为了避免凭猜测改代码，加了一套带时间戳的日志（`src/main/timing.ts` 的 `tlog`，
`+N.NNs` 表示进程启动后的秒数），覆盖整条启动链路，并逐轮缩小范围：

1. **怀疑：扩展加载被渲染进程阻塞 / MV3 SW 没有被主动拉起。**
   改为主进程启动时就 `loadExtensions()` 并对 MV3 扩展调用 `startWorkerForScope()`。
   结果：仍然 +30s。说明不是「没人去启动 worker」。

2. **怀疑：webRequest 回调没有触发，导致请求挂起 ~30s。**
   `recordUrlRequest` 用了只在窗口 focus 时才赋值的 `windows.current`，启动时为
   `undefined` 会抛异常，使 `onBeforeSendHeaders` 的 `callback` 不执行。
   做了防御性加固（始终调用 `callback`）。结果：仍然 +30s。

3. **怀疑：远程调试端口 / DevTools 自动附加导致 worker 暂停。**
   临时注释掉 dev 模式的 `remote-debugging-port`。结果：仍然 +30s。排除。

4. **关键证据 —— 页面正常，只有 worker 慢：**
   - 远程新标签页 `pcapp.rainsee.cn` 在 **0.6s** 内就 `did-stop-loading`，
     说明 view session 的网络 / webRequest / 适配器（adblock）管道完全正常。
   - `startWorkerForScope` 在 +2.5s 调用，promise 在 **waited 29.91s** 后才 resolve，
     worker 的第一行 JS 与 resolve 同一时刻（+30.4s）执行。
   - 加了 2 秒心跳：心跳 1→14 **稳定跳动**，主进程事件循环全程存活，
     说明**不是主线程被同步阻塞**。
   - 给 `chrome-extension://` 请求加了 webRequest 日志：`background.js` 的请求
     **完全没有经过 webRequest 管道** —— 说明卡顿发生在 worker 启动内部，
     在脚本被执行之前。

5. **定位根因：** worker「启动线程」被一个**同步 IPC**阻塞，直到 Chromium 的
   Service Worker `StartTimeoutTimer`（正好 30 秒）超时后才放行。

## 根因

`src/vendor/electron-chrome-extensions/renderer/index.ts` 的 `getI18n()`：

```ts
const getI18n = (extensionId: string) => {
  return ipcRenderer.sendSync('crx-i18n', extensionId)  // 同步、阻塞 IPC
}
```

i18n 工厂在 worker 初始化时**同步调用**它。但：

- `sendSync` 是阻塞调用；
- 在 **Service Worker** 上下文里，SW 的 IPC 是异步的、走 `sw.ipc`，
  而 `crx-i18n` 的同步处理器只注册在全局 `ipcMain` 上
  （见 `browser/api/i18n.ts`），SW 发出的同步消息**永远收不到回复**；
- 代码自身的注释（同文件、`i18n.ts:128-133`）也写明了 `sendSync` 在 SW 中不可用。

于是在 SW 中：`sendSync` 阻塞 worker 的启动线程 → 等不到回复 →
Chromium 的 `StartTimeoutTimer` 在 **30s** 时触发 → 同步调用被解除 →
worker 这才继续初始化并正常运行。

这解释了之前所有看似矛盾的现象：

| 现象 | 解释 |
|---|---|
| 每次都是约 30s | Chromium SW `StartTimeoutTimer`（30s）|
| 页面 0.6s 就加载完 | 页面 frame 的 `sendSync` 在 `ipcMain` 上**有**处理器；只有 SW 上下文没有可达的同步处理器 |
| 主线程存活（心跳一直跳）| 阻塞的是 **worker 启动线程**，不是主进程 |
| 没有 `chrome-extension://` 的 webRequest 日志 | 卡顿在 worker 初始化内部（preload 的同步 IPC），脚本还没运行 |
| 30s 后 worker 完全正常 | 超时放行后初始化照常完成 |

## 修复

在 `getI18n()` 中，遇到 Service Worker 上下文直接跳过同步路径（SW 本来就通过
异步的 `getI18nAsync` / `primeAsync` 预热 i18n 目录，功能不丢失）：

```ts
const getI18n = (extensionId: string) => {
  // sendSync 是阻塞 IPC。在 service worker 中没有可达的处理器
  //（SW 的 IPC 是异步、走 sw.ipc，而 'crx-i18n' 同步处理器在全局 ipcMain）。
  // 在这里调用会阻塞 worker 的启动线程，直到 Chromium 的 30s
  // StartTimeoutTimer 触发 —— 即扩展后台启动 ~30s 卡顿的根源。
  // Service Worker 通过 getI18nAsync 异步预热目录，所以这里直接跳过同步路径。
  if ((process as any).type === 'service-worker') {
    return null
  }
  try {
    return ipcRenderer.sendSync('crx-i18n', extensionId)
  } catch {
    return null
  }
}
```

修复后：`[ext-sw] alarm: init done` 在启动约 1~3s 内出现，
`startWorkerForScope resolved` 的等待时间降到不到 1 秒。

## 附带的防御性加固（非本次根因，但建议保留）

排查过程中顺手加固了两处「回调必被调用」的健壮性问题，避免将来真的出现请求挂起：

- `src/main/services/xiu-video.ts`：`recordUrlRequest` / `filterVideo` 用
  `findViewById()` 跨所有窗口查找 view（不再依赖只在 focus 时赋值的
  `windows.current`），并整体 try/catch，绝不抛出。
- `src/main/models/settings.ts`：view session 的 `onBeforeSendHeaders` /
  `onHeadersReceived` 处理器整体 try/catch，**保证 `callback` 始终被调用**。
- `src/main/services/adblock.ts`：`chrome-extension://` 资源直接放行，不进过滤；
  并对适配器回调做了「始终回调」的兜底。

## 主进程主动启动 MV3 后台（保留）

`src/main/sessions-service.ts` 现在在主进程启动时即加载扩展，并对 MV3 扩展调用
`startWorkerForScope()` 主动拉起后台 worker（与上游 electron-chrome-extensions
shell 的做法一致）。这不是本次 30s 卡顿的根因，但能让后台尽早就绪。

## 诊断代码清理

排查用的计时日志（`src/main/timing.ts`、各处 `tlog`/心跳、`chrome-extension://`
请求日志、adblock 放行日志）属于临时诊断代码，确认修复稳定后可移除。
